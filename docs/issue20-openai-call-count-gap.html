验收要求什么

Worker and UI tests use observable OpenAI call counts to cover confirmation, sequential progress, failure continuation, Cancel, Local-only precedence, and later reconfirmation.

六种行为，每一个都要用可观测的 OpenAI 请求次数证明。 现状是相关测试 63 项全绿，但没有一个数字来自真实 HTTP 出口： 计数全部发生在替身内部。替身只能回答「调度逻辑打算发几次」， 只有出口才能回答「OpenAI 实际收到了几次」。

每页操作实际产生的请求数

下文所有数字的前提，已经对着 CaptureService.ts 核实。

操作 每页 HTTP 请求数 构成
Add AI features（enrich） 2 1 × chat/completions（打标）+ 1 × embeddings（整页 token chunks 批量一次）
Re-index semantic search 1 embeddings
Hybrid 查询 1 query embedding（不属于批量，仅供对照）

六种行为逐条对照

验收行为 今天的证据 数的是哪个替身 缺的证据
confirmation 显示准确数量 handlers.test.ts 的 prepared 快照；Options.test.tsx 确认弹窗文案 响应对象快照 / UI 断言 「确认了 3 页」从未和「随后恰好发出 6 次请求」对过账
sequential progress BulkTaskRunner.test.ts 断言 runPage 触达顺序 传给 runner 的回调 mock 每页 chat 先于 embeddings、页面之间不并发，无从谈起
failure continuation 同文件构造 runPage 抛错后继续 回调层面的 failed 加一 provider 判定不可重试（400/401）时，整链的请求序列没有断言
Cancel canceled 进度事件 + Options 终态；provider 单元层证明撤销 maySend 后 retry 不再 fetch cancel() 返回值、进度事件、provider 内部 spy 取消点之后全局 fetch 增量为零没有被量过
Local-only precedence handlers.test.ts 让 mocked gate 从 true 翻成 false modeStore 替身的读数 真实模式翻转是否掐断下一次 fetch 未证
later reconfirmation 同文件第二个 begin 输入的 shouldContinue 再次为 true runner 输入替身 重新确认后的新增请求数从停点续接仍缺

补法：一个真件集成套件

新建 src/worker/handlers.integration.test.ts（与已有的 CaptureService.integration.test.ts 平行）。关键差异只有一个： BulkTaskRunner 用真的，OpenAIProvider 用真的， fetch 用 spy 换掉全局。 

// src/worker/handlers.integration.test.ts
const fetchSpy = vi.fn();
beforeEach(() => vi.stubGlobal("fetch", fetchSpy));
afterEach(() => vi.unstubAllGlobals());

function makeRealDeps(): HandlerDeps {
  const pageRepo = new PageRepo();          // fake-indexeddb/auto 已全局生效
  const chunkRepo = new ChunkRepo();
  const openai = new OpenAIProvider([0, 0, 0]);   // 重试瞬时化，计数才确定
  const captureService = new CaptureService(pageRepo, undefined, pageRepo,
                                           openai, chunkRepo, openai);
  const apiKeyStore = memoryKeyStore();     // 内存实现，仿 ChromeApiKeyStore 接口
  const modeStore = memoryModeStore();      // 可变状态，供场景中途翻转
  return {
    captureService,
    pageRepo,
    apiKeyStore,
    modeStore,
    testConnection: testOpenAIConnection,
    retrievalService: new RetrievalService(chunkRepo, pageRepo, openai, apiKeyStore),
    bulkRunner: new BulkTaskRunner(),       // 关键：不再是 vi.fn()
    semanticIndex: { embeddingModel: openai.embeddingModel, indexVersion: SEMANTIC_INDEX_VERSION },
    broadcast: () => {},
    autoSaveSettings: memoryAutoSaveSettingStore(),
  };
}
// 场景即常规流程：先 handleRequest 存入 3 个 keyword_ready 页，
// prepare 拿 batchId，再 bulkEnrich，最后 expect(fetchSpy).toHaveBeenCalledTimes(N)。

stub 响应必须长成 parser 认识的样子：

场景与精确计数（N = 3 页）

场景 干预时机 全局 fetch 终值 批内账目
全部成功 不干预 6 p1..p3 各 2 次，三页 ready
失败后继续 p2 的打标调用返回 400 5 p2 计 1 次即断、failed=1，p3 仍然继续
Cancel p2 的打标请求在途中点 Cancel 3 p1 完成两次；p2 在途的打标请求放行完成，其 embeddings 腿被授权撤销拦下；p3 不发起，进度报 canceled
Local-only 切换压过确认 p1 提交后立即切 local 2 p2/p3 维持 keyword_ready 且无 enrichmentError
后续重新确认跑完剩余 上一步之后恢复 hybrid 再 begin 2（累计回到 6） 新增恰为剩余 2 页 × 2
两页之间移除 key setApiKey("") 于页边界 2 handler 同时调 bulkRunner.cancel()，之后零增量

Semantic re-index 的对照版本把「每页 2 次」换成 「每页 1 次 embeddings」即可复用同一骨架。数字假设每页文本产出单次 embedBatch； 若未来分块策略改成多次上传，先更新本表。

实现注意

  • 构造器注入 [0, 0, 0] 让重试瞬时；或者用 400/401 这类不可重试状态码，两种手段都能保证「一页 = 已知请求数」。429/5xx 会吃满全部重试才抛，别用它们做计数断言。
  • 每个用例结束后清一次 Dexie（Dexie.delete() 或 repo 的 deleteAll），fake-indexeddb 是进程级的，脏数据会让下一案的计数漂移。
  • 不依赖 OPENAI_API_KEY，CI 任何环境可跑；这也意味着它可以放在 PR 必跑集里。
  • 验收里「UI tests」的一半不必强求穿透到真实 HTTP。合理读法：worker 侧拿这份计数证据，UI 侧在 Options.test.tsx 里补一行注释映射即可，在 issue 评论中说明对应关系。

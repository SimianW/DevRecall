## What happened this session

### 1. M5 was never merged into `dev` (fixed)

`dev` was running the **M4 keyword-only** `RetrievalService` — no vector arm,
`matchReason` hardcoded to `"keyword"`. The full M5 hybrid code lived only in
branch `worktree-m5`. Symptom: synonym queries returned nothing, and matches
never showed "meaning". **Fix:** fast-forwarded `worktree-m5` into `dev` (clean
FF, no conflicts). `dev` advanced from `88536ef` to the hybrid code.

### 2. Capture only saw the page shell, not the article (fixed — commit `a6613dd`)

Brightspace/D2L pages (e.g. `learn.uwaterloo.ca`) render the real article inside
a child `<iframe>`; the top frame is just LMS navigation + a "Loading…"
placeholder. The old extractor ran Readability on the **top document only**, so
the DB stored the shell, not the article — search had almost nothing to match.

**Fix** (`src/worker/services/CaptureService.ts`, `manifest.config.ts`):

- Content script now injects with `all_frames: true`.
- `ChromePageExtractor.extract` enumerates injectable frames via a no-op
`chrome.scripting.executeScript({ allFrames: true })` (reuses the already-
granted `scripting` permission — deliberately **avoids `webNavigation`**,
whose "read your browsing history" warning conflicts with the local-first
privacy posture), runs Readability per frame, and keeps the richest body via
`mergeFrameExtractions`, **anchoring url/title to the top frame** (the iframe's
own url must not become the saved page's identity).
- `mergeFrameExtractions` is a pure, unit-tested function.

Known, accepted limitation: Readability strips trailing link-heavy
**reference/citation lists** as boilerplate. That is why searching `Grammarly`
(which appeared *only* in the article's References list) returns nothing while
`Shopify`/`Canva` (also in body prose) hit. The main body is fully captured —
verified by searching `hyperlinks`, which returns the last real content section.
This is correct Readability behaviour, not a bug.

### 3. Empirically characterised the vector arm

Added a measurement harness (see [below](#the-measurement-harness)) and ran it
against the live `text-embedding-3-small` model. **Key, somewhat
counter-intuitive findings** — these drive every recommendation in this doc:


| query                    | cosine vs target chunk | passes 0.4? | what it means                                                              |
| ------------------------ | ---------------------- | ----------- | -------------------------------------------------------------------------- |
| `one-pager`              | **0.506**              | ✅ yes       | passage's *topic* IS one-pager → high                                      |
| `hyperlinks`             | 0.384                  | no          | exact but peripheral word → correctly keyword-only                         |
| `reporting`              | 0.275                  | no          | morphological variant — **correctly points to the right chunk**, but < 0.4 |
| `tiny fraction of users` | 0.267                  | no          | genuine paraphrase — **correctly points to right chunk**, but < 0.4        |
| `report`                 | 0.223                  | no          | correctly points to right chunk                                            |
| `small`                  | 0.155                  | no          | **exact word present in chunk, still ~noise**                              |
| `little`                 | 0.129                  | no          | synonym — *below* its own distractor score (noise)                         |


Takeaways:

1. **Embeddings encode the passage's overall topic, not word presence.** `small`
  is literally in its chunk yet scores 0.155, because the chunk is "about" a
   Chrome browser release, not "about" smallness. `one-pager` scores high only
   because the whole passage *is* about one-pagers.
2. **Single/peripheral keyword queries are intrinsically low-cosine** vs long
  passages and belong to the **keyword arm**. The hybrid split is working as
   designed.
3. **The vector arm shines for conceptual / natural-language queries** — later
  confirmed live: `Chrome new release` lit up **keyword + meaning**.

### 4. Verified retrieval logic is correct (live, by the user)

Two articles loaded. Cross-article searches discriminate cleanly (Chrome-only
terms never surface the one-pager and vice-versa). `one-pager` and
`Chrome new release` correctly show **keyword + meaning**; exact/peripheral words
show **keyword**. The user independently discovered the `stakeholder` vs
`stakeholders` gap — which is exactly the stemming task.

## The stemming task (M6 plan — Task 1)

> This is **Task 1 of the M6 plan**, which has the TDD checklist and file list.
> The detail below is the implementation rationale and constraints behind it.
> Stemming is **runtime-only in `tokenize()`, so it needs NO re-index.**

### Problem

The keyword (BM25) arm matches tokens **exactly** after lowercasing. There is no
stemming, so morphological variants miss:

- Searching `**stakeholder`** → **no results**. The article contains the plural
`stakeholders`. (Confirmed live.)
- Searching `**reporting`** → **no results**. The article contains `report` /
`reports`. (Confirmed by measurement; vector = 0.275, below the 0.4 floor, so
the vector arm can't save it either.)
- Searching `**report`** → works (exact token present).

This is a deterministic gap affecting any singular/plural or verb-form mismatch,
on **every** page, not just these examples.

### Root cause

`src/lib/bm25.ts`, `tokenize()` (line ~49). The Latin-token path (lines ~64–69)
lowercases, splits on `[^a-z0-9]+`, drops stopwords, and pushes the **raw**
token. No normalisation of word form.

### The fix

**Apply an English stemmer to Latin tokens inside `tokenize()`.** Because
`tokenize()` is called for **both** the query (bm25Search line ~108) and every
document (line ~116), stemming there normalises **both sides** automatically —
`reporting`→`report`, `stakeholders`→`stakehold(er)`, etc. — so they match.

**Precise insertion point:** the English branch around **line ~68**, where each
non-stopword Latin token is pushed. Stem the token there before `tokens.push`.

```ts
// inside the Latin-token loop, line ~67-69
for (const token of lower.slice(i, j).split(/[^a-z0-9]+/)) {
  if (token.length > 0 && !STOPWORDS.has(token)) {
    tokens.push(stem(token));   // <-- add stemming here
  }
}
```

### Hard constraints

1. **Do NOT stem the CJK bigram path** (line ~60). Stemming is English-only.
  Apply it strictly to the Latin/ASCII branch. The CJK bigram tokenisation must
   remain byte-for-byte unchanged (it has its own tests).
2. **Keep the bundle light.** This is an MV3 extension; the build already warns
  about chunk size. Prefer a tiny dependency-free Porter stemmer (a self-
   contained Porter implementation is a few KB) or a minimal `snowball`-style
   lib. **No WASM, no multi-MB NLP packages.**
3. **Stem at the same place for query and document** — i.e. inside `tokenize()`
  — so the two sides can never drift out of sync. Do not stem in one arm only.
4. **Bump the version** (`package.json` + `APP_VERSION` in
  `src/shared/messages.ts`) and commit. Project rule: every code change bumps
   the 4-part version `X.Y.Z.N` and is committed. Next would be `0.5.4.5`.

### TDD — write these failing tests first

In `src/lib/bm25.test.ts` (or a new sibling), red-first:

1. `tokenize("reporting")` and `tokenize("report")` produce the **same** stem.
2. `bm25Search("stakeholder", ["...engaging stakeholders on scope..."])`
  returns a hit (singular query → plural document).
3. `bm25Search("reporting", ["...a one-pager report ..."])` returns a hit.
4. **Regression guard:** an existing CJK test still passes unchanged — stemming
  must not touch CJK bigrams. Add an explicit assertion that
   `tokenize("报告")` is identical before/after.
5. Stemmer doesn't mangle short/code-like tokens into collisions that hurt
  precision (spot-check a couple of common dev terms, e.g. `css`, `json`).

Then implement the stemmer, watch them go green, run the full suite.

### Definition of done

- `stakeholder` and `reporting` both return the one-pager article.
- All 153 existing tests still pass (especially CJK bm25 tests).
- `typecheck` / `lint` / `build` clean.
- Version bumped + committed.

## Why NOT just lower the vector threshold

The previous M5 handoff suggested lowering `MIN_VECTOR_SCORE` (0.4) to fix
synonym recall. **We measured this with the live model and it is refuted for
single-word synonyms:**

- `little` (the reported "→ small" miss) scores **0.129** against the chunk it
should match — which is **lower** than its score against an unrelated chunk
(0.131). The correct match is *below the noise floor*. **No threshold can admit
`little`→`small` without admitting essentially everything.**
- `small` (exact word, present in chunk) is only 0.155, also in the noise.

So pure single-word synonyms (`little`→`small`) are **out of scope** for the
vector arm — they'd need a thesaurus / query expansion, which we are explicitly
**not** doing now.

### Optional, lower-priority: lower threshold 0.4 → 0.3

Separately, the data shows 0.4 is **too high for the vector arm's actual job**
(conceptual/paraphrase queries): genuine paraphrases like
`tiny fraction of users` (0.267) and `reporting` (0.275) **correctly identify
the right chunk** but get filtered out. Lowering `MIN_VECTOR_SCORE` to ~0.3
(in `src/worker/services/RetrievalService.ts`) would recover these.

**Caveat:** measured on a 3-chunk toy corpus, so the false-positive estimate is
weak. On a large corpus, distractor maxima rise. Recommend **0.3** (conservative)
over 0.25, and ideally re-validate on a bigger chunk set before committing. This
is a nice-to-have, **not** a substitute for stemming.

## Out of scope / known limitations (do not "fix" these)

- `**little` → `small`** and other pure synonyms: below the embedding noise
floor. Needs query expansion/thesaurus. Deferred.
- **References/citation lists dropped by Readability** (e.g. `Grammarly`): correct
Readability behaviour; main body is fully captured. Not a bug.
- `**small` returns the Chrome page via keyword**: it's a literal token match.
Expected. Suppressing it would require stopword/down-weighting work — separate
topic, not requested.

## The measurement harness

Run it to re-measure cosine for representative query/chunk pairs against the live
model (needs your own key; the key never appears in output):

```bash
OPENAI_API_KEY=sk-... pnpm test src/lib/vectorThreshold.measure.test.ts
```

It reuses `OpenAIProvider.embedBatch`, so model + L2 normalisation exactly match
production (cosine == dot product on normalised vectors). Columns: `target` =
cosine vs the chunk the query *should* recall; `best` = max cosine across all
chunks (`*` = top chunk is NOT the target → false-positive risk).
